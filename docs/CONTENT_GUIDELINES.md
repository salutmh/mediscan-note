# 콘텐츠 작성 규칙 (CONTENT_GUIDELINES)

> 대상: 케이스를 등록하는 사람, 해설을 쓰는 사람, 그리고 이 리포에서 작업하는 AI 에이전트.
> 최초 작성 2026-09-08 / 관련: `docs/RELEASE_READINESS.md`, `backend/README.md`

---

## 0. 이 문서가 있는 이유

**우리는 의료인이 아니다.** 그런데 이 서비스는 학습자에게 "당신이 표시한 영역이 기준과
얼마나 맞는지"와 "이 영상에서 무엇을 봐야 하는지"를 말한다. 근거 없는 문장이 하나라도
섞이면 그건 잘못된 의학 정보를 가르치는 것이 된다.

그래서 콘텐츠를 **출처별로 분리**하고, 각 출처가 지켜야 할 규칙을 여기 못박는다.
빈 채로 두는 것은 허용된다. **지어내는 것은 허용되지 않는다.**

## 1. 콘텐츠 4층 — 무엇이 어디서 오는가

| 층 | 필드 | 출처 | 누가 만드나 | 비어도 되나 |
|---|---|---|---|---|
| 계산된 사실 | `explanation.case_facts` | 전문가 GT + DICOM 태그에서 **계산** | 스크립트 | ❌ 필수 |
| 문헌 일반론 | `explanation.disease_info` | 질환 문헌 (출처 URL·확인일 필수) | 사람이 작성 + 출처 표기 | ✅ |
| 케이스 소견 | `explanation.case_findings` | **전문가가 이 케이스를 보고 작성** | 의료 전문가 | ✅ |
| 공간 피드백 | `spatial_feedback` | 두 마스크의 **geometry** | 자동 계산 | ✅ (마스크 없으면 null) |

**섞지 않는다.** 각 블록은 자기 `source` 를 들고 다니고, 화면도 시각적으로 분리해서 보여준다.
문헌 일반론을 이 케이스의 소견처럼 쓰면 안 되고, geometry 결과를 영상 소견처럼 쓰면 안 된다.

## 2. GT(정답 마스크) 사용 원칙

1. **전문가 GT 를 후처리하지 않는다.** 최소 면적 필터, 구멍 메우기, 스무딩, 경계 정리 전부 금지.
   보기 좋게 다듬는 순간 그것은 더 이상 전문가가 검수한 것이 아니다.
2. 병변 시작/끝 slice 의 작은 파편(2~24px)도 **그대로 등록한다.**
3. **채점 기준은 GT 뿐이다.** 모델 예측을 정답으로 쓰지 않는다. AI 가 완전히 실패한 케이스
   (VS-SEG-204)에서도 학습자 채점은 정상 동작해야 한다.
4. 기준 마스크가 없는 케이스는 **채점하지 않는다** (422, 이력도 남기지 않음). 근사로 때우지 않는다.
5. 사용자가 칠한 ROI 도 보정하지 않는다 (`fill_holes` 자동 적용 금지).

## 3. 케이스 등록 규칙

- 등록은 `python -m scripts.import_cases <manifest>` 로만 한다. DB 를 직접 수정하지 않는다.
- 파이프라인은 **DICOM → npy → 육안 검수 → PNG 자산 → 등록** 4단계로 나눈다.
  중간에 사람이 확인하는 지점을 남기기 위해서다. 단계를 건너뛰지 않는다.
- 케이스 = volume 1개. 슬라이스 자산은 **원본 slice_index 를 그대로 보존**한다 (재번호 금지).
- 좌/우 편측성처럼 **계산할 수 있는 사실은 추측하지 않고 DICOM 태그에서 계산한다.**
- 등록 후 `python -m scripts.verify_cases` 로 상태와 오래된 예측 sidecar 를 점검한다.
- 실제 의료영상·마스크·npy 는 **커밋하지 않는다** (`.gitignore`).

## 3-1. 케이스를 늘릴 때 — 무엇을 기준으로 고르는가

**아무거나 늘리면 편향이 생긴다.** 지금 6케이스는 우측 5 / 좌측 1 이고 크기도 한쪽에 몰려 있다.
이대로 30개로 늘리면 학습자는 "병변을 찾는" 훈련이 아니라 **"오른쪽을 칠하는" 훈련**을 하게 된다.

### 순서

```bash
# 1) 후보 스크리닝 — 볼륨을 만들지 않고 편측성·병변 크기만 잰다 (읽기 전용)
#    pydicom/rt_utils 가 필요해 학습 venv 로 돌린다
<학습리포>/.venv/Scripts/python -m scripts.screen_vs_seg_dataset     --data-root <VS-SEG DICOM 루트> --out data/vs_seg_screening.json --want 24

# 2) 사람이 후보를 확정한다 (추천 목록은 제안일 뿐이다)

# 3) 선택한 케이스만 export -> 육안 검수 -> 자산 생성 -> import
#    (backend/README.md "VS-SEG 실데이터 파이프라인" 참고)
```

### 고를 때 보는 것 (전부 계산되는 값)

| 기준 | 왜 |
|---|---|
| 좌/우 균형 | 한쪽에 몰리면 위치를 외우는 훈련이 된다 |
| 병변 크기 분포 | 큰 것만 있으면 너무 쉽고, 작은 것만 있으면 첫 사용자가 좌절한다 |
| AI 검출 성공/실패 | 둘 다 있어야 "AI 도 놓칠 수 있다"를 가르칠 수 있다 (VS-SEG-204) |
| 병변 slice 수 | slice 탐색 훈련의 폭 |

### 고를 때 **하지 않는 것**

- **의료적 난이도를 자동으로 매기지 않는다.** 크기·모델 성능은 계산값일 뿐 난이도가 아니다.
  `difficulty` 는 전문가 검토 대상이며 미지정이면 비워 둔다.
- **육안 검수를 건너뛰지 않는다.** 스크리닝은 "어떤 케이스를 볼지" 고르는 단계이고,
  GT 가 실제로 맞는지는 사람이 오버레이를 보고 확인한다.
- 스크리닝 스크립트는 **케이스를 등록하지 않는다.** 읽고 표를 낼 뿐이다.

## 4. `case_findings` (전문가 소견) 작성 규칙

### 4.1 누가 쓰나
**의료 전문가만.** 등록자가 대신 요약하거나, AI 가 생성하거나, 문헌에서 옮겨 적지 않는다.

### 4.2 필수 항목
| 필드 | 설명 |
|---|---|
| `findings` | 핵심 영상 소견 |
| `reviewer` | 검토자 식별자 (이름 또는 역할). **없으면 등록이 거부된다** |
| `reviewed_at` | 검토일 `YYYY-MM-DD`. **없으면 등록이 거부된다** |

> `reviewer`/`reviewed_at` 은 **검토 출처를 필수화**하는 장치다.
> 필드가 채워져 있다는 것만으로 검토가 이루어졌음을 보증하지는 않는다.

### 4.3 선택 항목 (학습용)
| 필드 | 설명 | 쓸 때 주의 |
|---|---|---|
| `lesion_location` | 병변 위치에 대한 설명 | 해부학 명칭은 전문가만 |
| `reference_region_note` | 기준 영역이 왜 그렇게 잡혔는지 | GT 를 근거로 |
| `learning_points` | 학습자가 확인할 포인트 (배열) | 이 케이스에 한정된 내용 |
| `common_mistakes` | 자주 놓치는 부분 (배열) | 관찰에 근거한 것만 |
| `medical_terms` | 용어 설명 | |
| `references` | 출처 | |
| `content_version` | 콘텐츠 버전 | 수정 이력 추적용 |

**비어 있으면 비운 채로 둔다.** 화면에서 해당 줄이 빠질 뿐이고, 그것이 정직한 상태다.

### 4.4 검토 상태 (`case_findings_status`)
| 값 | 뜻 |
|---|---|
| `needs_expert_review` | 아직 전문가가 보지 않음 — **현재 6케이스 전부 이 상태** |
| `in_review` | 검토 진행 중 |
| `approved` | 검토 완료. `case_findings` 에 실제 내용이 있다 |

- 상태는 DB(`cases.findings_status`)에 저장하지만, **소견이 실제로 없으면 `approved` 로 나가지 않는다.**
  상태 필드가 실제 내용과 어긋나도 응답이 거짓말을 하지 않게 하기 위한 보정이다.
- 상태만 올려서 "검토된 것처럼" 보이게 만드는 경로를 만들지 않는다.

## 5. `disease_info` (문헌 학습정보) 작성 규칙

- 위치: `backend/app/content/diseases/<disease_code>.json` (**git 커밋 대상** — 텍스트라 개인정보가 없다)
- **manifest 로 넣을 수 없다.** 등록자가 임의로 쓴 문장이 "문헌 기반"으로 표시되는 경로를 막기 위함이다.
- **이 질환의 일반적 특징만** 쓴다. "이 케이스에서 관찰된다"는 표현은 쓰지 않는다.
- 문장마다 **실제로 열어본 출처**를 표기하고, `references` 에 URL 과 `accessed` 날짜를 남긴다.
- 확인하지 못한 내용은 **넣지 않는다.**
- `source` 와 `notice` 는 파일 값을 쓰지 않고 **서버 상수**에서 채운다.

## 6. AI(에이전트)가 생성해도 되는 것 / 안 되는 것

### ✅ 생성해도 되는 것
- **geometry 계산 결과와 그 문장화** — 겹침 비율, 면적 비, 중심 거리, 과소/과대 표시 안내
  (`app/feedback.py`). "표시한 영역의 중심이 기준에서 벗어나 있습니다" 수준.
- 데이터에서 **계산된 사실** — 대표 slice 번호, 병변 slice 범위, 면적(px), DICOM 태그에서
  계산한 편측성.
- 코드, 테스트, 스키마, 파이프라인, 문서 구조.
- 이미 사람이 쓴 내용의 **형식 정리**(오탈자, 필드 이동). 내용 추가는 아니다.

### ❌ 절대 생성하면 안 되는 것
- **영상 소견** — 내이도 침범 여부, 조영증강 양상, 종괴 성상, 낭성 변화, 경계 특성 등
- **질환 추정·감별 진단·임상적 의미**
- **해부학적 해석** — "이 위치는 ~이므로" 류
- **문헌 내용의 창작** — 출처를 확인하지 않은 의학 일반론
- 전문가 소견란을 그럴듯한 문장으로 채우는 것 (비워 두는 것이 옳다)
- `reviewer` / `reviewed_at` 을 임의 값으로 채우는 것

> **판단 기준 한 줄**: 두 마스크의 픽셀만 보고 계산할 수 있으면 자동 생성해도 되고,
> 영상을 "읽어야" 알 수 있으면 전문가 몫이다.

이 규칙은 문서상 약속이 아니라 **테스트로 강제된다** —
`backend/tests/test_spatial_feedback.py::test_messages_never_contain_medical_claims` 가
자동 생성 문구에 의료 어휘가 섞이면 실패시킨다.

## 7. 채점 임계값

- 값은 `backend/app/scoring_config.py` 한 곳에서 관리한다.
- 현재 `match ≥ 0.60`, `partial_match ≥ 0.15` 이며 **교육적으로 검증된 값이 아니다.**
  응답에 `validation_status: "not_yet_educationally_validated"` 를 함께 내려보낸다.
- 임의로 바꾸지 않는다. 이미 저장된 제출 이력의 `grade` 는 바뀌지 않으므로 통계가 섞인다.
  조정할 때는 근거와 날짜를 `scoring_config.py` 의 "변경 이력"에 남긴다.
- 화면에서 이 값을 **확정된 의학 기준처럼** 표시하지 않는다.

---

## 8. 표현 규칙

- 평가는 **일치 / 부분 일치 / 불일치**(`match`/`partial_match`/`mismatch`).
  "정답/오답"처럼 확정적 의학 판단으로 읽히는 표현을 쓰지 않는다.
- "기준 마스크와의 일치 정도"라는 뜻이 드러나게 쓴다.
- 모든 AI 관련 출력에는 **학습 참고용이며 확정 진단이 아니라는 고지**가 함께 간다.
- 모델이 없으면 그럴듯한 결과를 만들지 않고 `model_unavailable` 로 사실을 말한다.
